# Jumao v0.4 产品规划：Agent 证据与计划质量

状态：产品方案已确认，开发进行中  
日期：2026-07-22  
基线版本：v0.3.1  
基线提交：`93d44fc0503124c88a571a97bbcad86c7514d96e`

## 1. 产品决定

建议把 v0.4 从原 Roadmap 中的“Skill Export”调整为：

> 让每个显示为 `completed` 的 Agent 都能说明为什么参与、看到了什么职责相关证据、产生了什么不可替代的结论，以及这条结论如何进入最终开发计划。

Skill Export 暂缓到后续版本。当前规划质量没有被证明之前，不扩大导出渠道。

v0.3.1 保持 immutable。本方案不回写 v0.3.1 tag、npm 包、macOS 发布物或 checksum。

## 2. 用户问题

v0.3.1 已经证明 44 个角色可以本地、确定性、串行、可审计地运行，但真实样例测试暴露了四类问题：

1. 同一语义换一种说法，可能触发不同角色。
2. 否定句中的关键词可能错误触发角色。
3. 平台不匹配的角色仍可能完成分析。
4. Agent 产出的专业任务没有充分进入最终 `tasks/jumao-agent-plan.md`。

用户最终关心的不是“有多少 Agent 亮起”，而是：

- 为什么这个角色与我的项目有关？
- 它依据了哪个回答、文件、配置或测试？
- 它发现了什么其他角色没有发现的事？
- 它的结论具体改变了开发计划中的哪一项？

## 3. 发现证据

2026-07-22 使用一个临时 Node 网页商品目录进行了两轮语义等价测试。

项目包含：

- 匿名商品浏览源码。
- 一条可运行的 Node 测试。
- GitHub CI 配置。
- 明确的匿名浏览、支付和发布保护边界。
- 增加邮箱登录和订阅规划的用户需求。

结果：

| 输入方式 | completed | skipped | blocked | failed |
|---|---:|---:|---:|---:|
| 英文 `login/subscription`，包含“不要发布上线” | 20 | 24 | 0 | 0 |
| 中文“登录/订阅”，不包含发布关键词 | 18 | 26 | 0 | 0 |

已确认的问题：

- 英文 `login` 未触发登录相关角色，中文“登录”可以触发。
- “不要发布上线”触发了 App Store、SRE、灰度和设备测试角色。
- Node 网页项目被识别为 Backend，Web 角色未参与。
- Web 项目的订阅需求触发了 iOS IAP 角色。
- 第一轮 20 个 completed Agent 重复引用同一组通用项目证据。
- 4 条产品保护规则分别在 20 个 Agent 输出中重复出现。
- 最终计划只要求读取文件和运行测试，没有形成登录、匿名兼容、会员状态和假数据方案等实际任务。

## 4. v0.4 产品目标

### 4.1 触发结果稳定

语义相同的用户描述，无论使用常见中文或英文表达，都应产生相同的适用角色集合。

### 4.2 否定意图可识别

“不要发布”“不接真实支付”“暂不做登录”等表达不能作为对应能力已经启用的证据。

### 4.3 平台边界优先

角色必须同时满足需求信号和平台适用性。Web 项目不能仅因出现“订阅”就触发 iOS IAP；没有 Apple 平台证据时不能触发 App Store 角色。

### 4.4 completed 有明确契约

一个 Agent 只有满足完成契约时才能标为 `completed`：

```text
明确触发原因
+ 职责相关的输入或项目证据
+ 独立发现、保护项、任务或阻塞问题
+ 对最终计划可说明的贡献
```

不满足时应当 `skipped`，并提供准确的跳过原因。

### 4.5 最终计划吸收专业结论

Agent 不是只生成审计记录。相关 Agent 的结论必须经过筛选、排序和去重后，进入最终开发计划。

## 5. 对外产品表述

面向普通用户统一使用：

> 44 个本地专业检查角色。

需要进一步解释时使用：

> 它们是确定性、可审计的职责角色，不是 44 个独立 AI 模型，也不调用外部 AI API。

界面和文档不得暗示：

- 44 个模型正在独立思考。
- 小组之间正在进行模型辩论。
- `completed` 代表角色已经进行了人类专家级全面审查。

## 6. 角色分层

保留现有 44 个职责，不在 v0.4 增加角色数量。

### 核心规划角色

直接帮助形成开发计划，例如：

- 项目负责人 / 创始人
- 产品经理
- UI / UX
- 安全 / 隐私
- 项目经理 / 研发负责人
- QA 测试
- 发布经理
- 文档 / 交付物

核心角色可以由明确用户意图触发，但输出必须标明证据属于 `intent`、`project` 还是 `file`，不能把通用工程文件包装成角色专属证据。

### 条件治理角色

只在对应产品能力、平台或风险真实出现时参与，例如：

- iOS、watchOS、Web、后端、数据库
- IAP、财税、客服、增长
- 健康声明、算法验证、备案、微信、短信
- SRE、灰度、设备实验室

条件角色必须同时通过需求信号、平台边界和职责证据检查。

## 7. Agent 完成契约

每个 Agent 输出需要在产品层面区分以下信息：

| 字段 | 含义 |
|---|---|
| `triggerReasons` | 为什么该角色参与，包含正向需求和平台条件 |
| `negativeSignals` | 用户明确排除的能力或阶段 |
| `intentEvidence` | 来自用户回答的直接证据 |
| `projectEvidence` | 来自平台、语言、构建系统和目录结构的证据 |
| `roleEvidence` | 与该角色职责直接相关的文件、配置或测试 |
| `findings` | 该角色独有的发现 |
| `protections` | 必须保护的已有行为和安全边界 |
| `tasks` | 能进入开发计划的可执行任务 |
| `blockingQuestions` | 缺少决定时真正阻止后续工作的少量问题 |
| `planContribution` | 该角色最终进入计划的内容和位置 |

通用的 `package.json`、语言或平台信息可以作为项目背景，但不能单独证明财税、IAP、医疗或上架角色已经完成专业分析。

## 8. 触发和平台规则

### 8.1 语义归一化

首版仍保持确定性规则，不引入模型 API。规则至少覆盖：

- 常用中英文同义词，例如“登录 / login / sign in / account”。
- 常见平台词，例如“网页 / Web / browser”。
- 功能与阶段的明确肯定表达。
- “不、不要、暂不、禁止、仅本地”等否定或限制表达。

### 8.2 正向信号与否定信号分离

示例：

| 用户表达 | 正确解释 |
|---|---|
| “准备发布” | 发布信号为正 |
| “不要发布” | 发布信号为负，不触发发布角色 |
| “增加订阅，但先不接真实支付” | 订阅规划为正，生产支付为负 |
| “保留匿名浏览，新增可选登录” | 登录规划为正，匿名浏览是保护项 |

### 8.3 平台兼容门

角色参与前先检查平台：

- IAP 和 App Store 需要 Apple 平台证据。
- watchOS 需要 Watch 证据。
- Web 工程师需要 Web 项目或网页交付证据。
- 短信和微信角色需要对应登录或消息渠道证据。
- SRE 和灰度需要真实上线、持续服务或生产运行意图。

## 9. 证据规则

### 可以作为角色证据

- 用户明确描述的功能或限制。
- 与职责相关的源码文件。
- 与职责相关的测试。
- 构建、CI、部署、权限或平台配置。
- 产品边界、数据安全、发布证明等真实文档。

### 不能冒充角色证据

- 仅仅存在 `package.json`。
- 仅仅检测到一种编程语言。
- 与职责无关但被所有 Agent 重复引用的同一文件。
- 由否定句截取出的孤立关键词。
- 当前项目平台不支持的能力。

### 证据扫描边界

继续保持：

- 默认只读业务源码。
- 跳过凭证、密钥、数据库和敏感文件。
- 对扫描深度、文件数和单文件大小保持明确限制。
- 计划中说明“保守证据匹配，不是完整依赖图”。

## 10. 最终计划合成

`tasks/jumao-agent-plan.md` 需要从相关 Agent 输出中形成真正的开发步骤。

合成顺序：

1. 用户明确目标和否定边界。
2. 真实影响文件和已有测试。
3. 核心规划角色给出的最小闭环。
4. 条件角色给出的必要前置任务和保护项。
5. 去重后的测试与发布检查。
6. 真正阻塞开发的问题。

每个进入计划的任务必须包含：

- 为什么需要做。
- 对应哪个 Agent 结论。
- 对应哪条用户意图或项目证据。
- 预计修改的最小区域。
- 可验证的完成条件。

对于登录和订阅样例，合格计划至少应包含：

- 保留匿名浏览的回归测试。
- 定义匿名、已登录和会员状态。
- 第一阶段只使用本地假账号和假会员状态。
- 明确不保存真实密码和支付信息。
- 明确真实后端、支付、退款和注销为后续阶段前置条件。
- Web 项目不得产生 StoreKit 或 App Store 实施任务。

## 11. 去重规则

- 同一条产品保护规则在 Agent 明细中可以被引用，但最终计划只出现一次。
- 相同任务由多个 Agent 提出时，合并为一个任务并保留多个来源。
- 通用安全边界与角色专属边界分开显示。
- 不通过简单截断隐藏重复问题；必须使用稳定的语义键或规则键去重。

## 12. 黄金样例矩阵

v0.4 开发前先固定以下测试项目和预期角色矩阵：

### A. 空白 iPhone 新项目

- 核心规划角色完成。
- iOS 角色完成。
- Web、后端、IAP、医疗等无证据角色跳过。

### B. 现有 Web 登录与订阅规划

- Web、后端、数据库、隐私、客服相关角色按证据参与。
- 保留匿名浏览。
- 不接真实支付时，不能产生生产支付任务。
- IAP 和 App Store 跳过。
- 否定发布不能触发 SRE、灰度和设备实验室。

### C. 本地 macOS 文件工具

- macOS 工程证据被正确识别。
- 不因“文件”二字触发云同步或数据库。
- 没有外部用户时，生产运营角色跳过。

### D. iOS 健康趋势应用

- 健康内容、医疗声明、算法证据、隐私和设备测试按明确能力参与。
- 没有诊断声明时，不生成诊断或治疗任务。

### E. 普通 Node CLI 改动

- 正确识别 CLI，不误判成生产后端服务。
- 重点落在现有命令、测试、兼容性和发布证据。
- 页面、App Store、IAP 和移动设备角色跳过。

每个黄金样例都必须固定：

- 44 个角色的预期状态。
- 每个 completed 角色的最低证据要求。
- 最终计划必须出现的任务。
- 最终计划禁止出现的任务。

## 13. v0.4 验收标准

### 触发准确性

- 语义等价的常见中英文输入产生相同角色状态。
- 否定发布不会触发发布角色。
- 否定真实支付不会生成生产支付任务。
- 平台不兼容角色不得 completed。

### 证据真实性

- 每个 completed Agent 至少有一个清楚的触发原因。
- 条件角色至少有一条职责相关证据。
- 通用工程文件不能作为所有角色的专属证据。
- skipped 原因必须说明缺少的是信号、平台还是职责证据。

### 计划质量

- 相关 Agent 的任务能够进入最终计划。
- 最终计划包含具体实施对象和完成条件。
- 重复保护项只显示一次。
- 不产生用户未要求且平台不支持的任务。
- 最终计划继续要求 Codex 在修改代码前先复述目标和边界。

### 稳定性与安全

- 仍然记录全部 44 个角色的状态。
- 仍然按确定性顺序执行。
- 相同输入和相同 workspace 产生稳定结果。
- 不调用外部 AI API。
- 不需要 API key 或 Jumao 账号。
- 扫描阶段不修改业务代码。
- 不自动发布、收费、部署或操作外部平台。

## 14. 建议实施阶段

### 阶段 1：黄金样例和预期矩阵

先把五类样例、角色状态、必须任务和禁止任务写成可重复验证的基准。

### 阶段 2：意图与平台判断

实现中英文归一化、否定信号和平台兼容门，先解决误触发与漏触发。

### 阶段 3：角色证据契约

区分通用上下文和职责证据，重新定义 completed 与 skipped。

### 阶段 4：计划合成

让 Agent 的独立任务、保护项和问题真正进入最终计划，并完成稳定去重。

### 阶段 5：用户解释与兼容验证

在 UI 和文档中解释“本地专业检查角色”，验证旧 workspace、CLI JSON、JSONL 事件和 Jumao Cat 状态恢复兼容。

## 15. 非目标

v0.4 不做：

- 不增加第 45 个 Agent。
- 不把 44 个角色改成 44 个大模型调用。
- 不加入外部 AI API。
- 不改成并行模型讨论系统。
- 不做自动代码修改。
- 不做自动部署、发布或付费操作。
- 不以 GUI 自动化缺口阻止核心 Runtime 发布。
- 不在本版本做 Skill Export。
- 不修改任何 v0.3.1 发布物。

## 16. 已确认的开发决定

项目主人已于 2026-07-22 确认：

1. v0.4 正式替换原 Roadmap 的 Skill Export 目标。
2. Skill Export 顺延到 v0.5 或更后版本。
3. 接受“核心规划角色 + 条件治理角色”的产品分层。
4. 接受本文件中的五类黄金样例作为发布门槛。

开发仍需按阶段提交真实测试证据；本确认不代表 v0.4 已完成或已发布。
